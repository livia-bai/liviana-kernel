# 写时复制 B 树

涉及文件：`src/btree.zig`（节点格式、节点内的操作）、`src/ctree.zig`（写时复制、事务、挂载、检查）；用到 `src/bio.zig`（[disk.md](disk.md#缓冲区缓存biozig)）

以后的文件系统建在一棵写时复制（copy-on-write）的 B 树上，思路照 btrfs：所有元数据都是树里按键排好序的条目，改树时从不改动已经提交的块，所以不需要日志也能保证掉电之后磁盘上是完整的。现在还只是这棵树本身，还没有接进内核（没有文件、目录），只在单元测试里用，用一块内存当磁盘。

和 btrfs 比，简化掉了：extent tree（btrfs 用另一棵树记每个块的引用，这里挂载时走一遍树算出来）、快照和子卷、多设备、校验和树、节点的合并和借条目、细粒度的树锁。

## 磁盘布局

| 块 | 内容 |
| --- | --- |
| 0、1 | 两个超级块槽位，事务号为 g 的超级块写在第 `g % 2` 块 |
| 2 起 | B 树的节点（以后还有文件数据），从哪里分配由空闲位图决定 |

```zig
pub const Super = extern struct {
    csum: u32,              // crc32c，覆盖这一块 csum 之后的所有字节
    _pad: u32,
    magic: [8]u8,           // "LBFS0001"
    generation: u64,        // 事务号
    blocks: u64,            // 文件系统有多少块
    root: u64,              // 根节点的块号
    root_generation: u64,   // 根节点的事务号
    root_level: u8,         // 根节点的层数（树高 - 1）
    _pad2: [7]u8,
};
```

所有整数都是小端，结构体都是 `extern struct`：内核（RISC-V）、主机上的单元测试、以后的 `mkfs` 看到的布局一样。

## 节点格式（`btree.zig`）

每个节点正好一块（4 KiB），开头是 24 字节的 `Header`：

```zig
pub const Header = extern struct {
    csum: u32,          // crc32c，覆盖这一块 csum 之后的所有字节
    nritems: u16,
    level: u8,          // 0 是叶子
    _pad: u8,
    blockno: u64,       // 这一块自己的块号
    generation: u64,    // 写它的事务号
};
pub const Key = extern struct { objectid: u64, offset: u64, type: u8, _pad: [7]u8 };   // 24 字节
pub const Item = extern struct { key: Key, offset: u32, size: u32 };                   // 32 字节
pub const Ptr = extern struct { key: Key, blockno: u64, generation: u64 };              // 40 字节
```

**键**和 btrfs 一样是三元组，先比 `objectid`、再比 `type`、最后比 `offset`。以后文件系统用 `objectid` 表示 inode 号，`type` 表示条目的种类（inode、目录项、文件数据……），`offset` 的意思由种类决定；同一个文件的所有条目挨在一起。树本身只把它们当三个数比较。

**叶子**：

```
Header | Item 0 | Item 1 | ... | Item n-1 |  空闲  | 数据 n-1 | ... | 数据 1 | 数据 0
```

条目按键从小到大排在前面，每个条目的数据从块的末尾往前放：第 0 个的数据在最后，第 i 个紧挨在第 i-1 个的前面（btrfs 的布局）。中间是空闲空间。

- 插入第 i 个：第 i 个以后的条目往后挪一格，它们的数据整体往前挪新数据的长度，新数据放在第 i-1 个的数据前面（`leafInsert`）。删除反过来（`leafRemove`）。
- 一个条目的数据最多 `max_data` = `leaf_space / 4 - 32` = 986 字节（`leaf_space` = 4096 - 24）。这保证叶子满了从中间分开以后，两边都至少空出 `leaf_space / 4`，新条目放哪边都放得下，分裂一次就够（btrfs 允许更大的条目，有时要分成三份）。
- **分裂**（`splitLeaf`）按字节数从中间分：前一半的条目和数据加起来刚超过总数的一半为止，后一半搬到新叶子。后一半的数据正好在数据区的最前面，原来的叶子直接截掉，前一半一个字节都不用动。

**内部节点**：

```
Header | Ptr 0 | Ptr 1 | ... | Ptr n-1 |  空闲
```

- 第 i 个子节点里的键都 `>= ptrs[i].key`、`< ptrs[i+1].key`。往下走时找最后一个 `key <= 目标` 的指针（`childFor`）。
- **`ptrs[0].key` 不参与查找，当作负无穷**。往最左边插入比所有键都小的键时，它走第 0 个子节点，不用回头改父节点的键（btrfs 要 `fixup_low_keys`）。代价是 `ptrs[0].key` 可能过时：第 0 个子节点插进了更小的键、又分裂过之后，它会比 `ptrs[1].key` 还大，甚至比父节点给的上界还大。所以哪里都不看它，检查时也跳过它。
- 别的键是下界，不一定正好是子节点的第一个键：删掉子节点的第一个条目之后父节点的键不改，仍然是对的下界。
- 一个内部节点最多 `(4096 - 24) / 40` = 101 个指针；单元测试里故意设成 5（`builtin.is_test`），少量数据就能长出好几层。分裂（`splitPtrs`）从中间分，后一半的第一个键往上交给父节点当分隔键：它至少是原来的第 2 个，不会是过时的 `ptrs[0].key`。

**校验**：节点和超级块都带 crc32c（`std.hash.crc.@"CRC-32/ISCSI"`）。节点的 `blockno` 能发现磁盘把数据写错了地方，`generation` 和父节点指针里记的对不上说明这次写丢了（磁盘上还是旧内容）。读节点时（`ctree.readNode`）核对：从磁盘读进来的验校验和（`bio.load` 返回这次真的读了盘；缓存里的验过了，不再算），块号、事务号、层数每次都核对，内部节点不能是空的。对不上就是 `Corrupt`，并把缓冲区标成无效，下次重新读盘。

## 写时复制（`ctree.zig`）

已经提交的树（超级块指向的那棵）上的块**从来不改**。要改一个节点：

```zig
fn cow(v: *Volume, b: *bio.Buf) Error!*bio.Buf {
    if (b 的 generation == v.transid) return b;   // 这个事务里已经复制过，直接改
    新块 = v.alloc();  复制整块;  改新块的 blockno、generation = transid;
    v.free(旧块号, 旧 generation);  放开 b;  返回新块
}
```

复制了一个节点，它的父节点就要改成指向新块，父节点也要先复制……所以每次修改都**从根到叶子把整条路径复制一遍**（`descend`），拿着路径上所有的缓冲区，最后一起写盘（`Path.finish`）。同一个事务里第二次改同一个节点不再复制。

### 插入

1. 先只读地查一遍（`lookup`）：键已经存在就返回 `Exists`，什么都没动。
2. **预留**：最坏情况下，路径上每一层复制一次、分裂一次，再长出一个新根，需要 `2 × 树高 + 1` 个空闲块。不够就返回 `NoSpace`，什么都没动。所以磁盘满不会在做到一半时才发现。
3. `descend`：从根走到叶子，路上每个节点 `cow`，父节点的指针改成新块号和当前事务号。
4. 叶子放得下就插进去；放不下就分出一个右兄弟，新条目放进该放的那一半，再把 `{ 右兄弟的第一个键, 它的块号 }` 插到父节点里路径那一格的后面（`insertPtr`）。父节点满了接着分裂，一直到根；根也满了就长出一个新根（两个指针：旧根和它分出来的兄弟），树高一层。
5. `Path.finish`：改过的节点和新分配的节点写盘（写之前算校验和），放开缓冲区。

因为拿着整条路径，分裂可以从下往上传，不用像 btrfs 那样一边往下走一边提前分裂。路径最多 8 层（`max_levels`），加上每层最多分出一个节点，同时拿着的缓冲区远少于缓存的 32 个。

### 删除

查到、预留（树高个块）、`descend` 之后从叶子里删掉条目。叶子删空了（而且不是根）就释放它、把它从父节点里摘掉；父节点也空了接着往上。最后，根是只有一个指针的内部节点时，让那个子节点当根（`collapseRoot`），树矮一层。

**不合并半空的节点**（btrfs 会和兄弟合并、借条目）：简单，代价是删得多了会留下一些半空的节点，树也不会因此变矮。内部节点至少有一个指针，根要么是叶子、要么至少两个指针（只剩一个就塌下去）。

### 更新

长度不变时就地改（`descend` 之后改叶子里的数据）。长度变了就删了再插，一开始按两步加起来的最坏情况预留。

### 查找和遍历

`lookup` 和 `next` 不复制，从根往下走时只拿着一个缓冲区（读出子节点的块号就放开父节点）。

- `lookup(key, out)`：键正好相等的条目，把数据复制进 `out`（最多 `out.len` 字节），返回数据长度。
- `next(key, out)`：第一个键 `>= key` 的条目，遍历时下一次从 `found.key.successor()` 开始。走到叶子的末尾时，用往下走时记下的“下一个叶子的下界”（右边还有兄弟的最深那一层的下一个键）重新查。

## 事务和提交

```zig
pub const Volume = struct {
    generation: u64,     // 磁盘上最新的超级块的事务号
    committed: Root,     // 它指向的根
    transid: u64,        // 当前事务 = generation + 1
    root: Root,          // 当前的根
    used: Bitmap,        // 用着的块：当前的树、已提交的树、超级块
    pending: Bitmap,     // 已提交的树用着、当前的树不用了的块
    free_count: u64,
    ...
};
pub fn format(blocks: u64) Error!void
pub fn mount(v: *Volume) Error!void
pub fn commit(v: *Volume) Error!void
pub fn abort(v: *Volume) Error!void
pub fn insert / update / delete / lookup / next
pub fn check(v: *Volume) Error!Stats
```

**新节点在每次操作结束时就写下去了**：它们都在已提交的树没用着的块上，什么时候写、写到一半掉电，都不影响已提交的树。**提交只写一个超级块**，让它指向新的根：

```
commit:  写超级块（事务号 transid，写到第 transid % 2 块） → pending 里的块变成空闲 → generation = transid，transid += 1
```

写超级块就是“一下子从旧树换成新树”的那一刻：写完之前掉电，磁盘上最新的超级块还指向旧树，旧树的块一个都没动过；写完了就是新树。这就是写时复制文件系统不需要日志的原因。当前事务什么都没改时，`commit` 不写超级块。

**两个槽位轮流写**：超级块写到一半掉电，校验和就对不上；`mount` 读两个槽位，用校验和对、事务号大的那个，于是退回上一个事务。那棵树还完整，因为——

**释放的块要等提交之后才能再用**。一个块在事务 g 里不再被当前的树用了（被复制走了、节点被删了）：

- 它是事务 g 自己分配的（`generation == transid`）：已提交的树没用它，马上空出来。
- 否则它属于已提交的树（事务 g-1 的），记进 `pending`，等事务 g 的超级块写完才空出来。提前空出来的话，事务 g 接下来分配到它、改写它，这时掉电，磁盘上的超级块还指向事务 g-1 的树，而那棵树已经被改坏了。

反过来，事务 g 提交之后释放的事务 g-1 的块，可能马上被事务 g+1 改写；那时候磁盘上的两个超级块是 g（完整）和 g-1（它的树开始被改写）。只要 g 的超级块是好的，挂载就不会用 g-1，所以没关系；`g+1` 的超级块写到一半掉电，它占的正是 g-1 的槽位，挂载用 g。

**分配用 first fit**：编号最小的空闲块。刚空出来的块马上会被重用，所以哪里提前放出了已提交的树的块，掉电测试马上就能撞上；按顺序往后找（next fit）要绕一圈才会重用，开发时它掩盖了这种错误（见下面的测试）。

**空闲空间不存在磁盘上**：`mount` 从根把树走一遍（`walk`），用到的块记进 `used`。这样磁盘上没有一份“哪些块空闲”的记录需要和树保持一致，掉电也就不会让它们不一致。代价是挂载要读整棵树（以后文件的数据块也要从树里的条目算出来）。btrfs 用 extent tree 记每个块的引用，挂载时不用走树，但那棵树自己也要写时复制、和分配互相牵扯，复杂得多。位图是静态的，每块一位，最多管 65536 块（256 MiB），一个位图 8 KiB。

**出错时整个事务作废**（`abort`）：操作做到一半出错（读到坏块），树可能改了一半。这时根退回 `committed`，重新走一遍已提交的树算出用着的块（和挂载一样）。当前事务写下去的节点都在已提交的树没用的块上，不用管。以后文件系统每个系统调用提交一次，出错只丢这一次的改动。磁盘满不会走到这一步（先预留）。

**位图不能在栈上复制**：一个位图 8 KiB，`Volume` 有三个（`used`、`pending` 和走树用的 `seen`），比内核栈的一半还大。只在原地改（`clear`、逐个 `masks` 的循环），不写 `.initEmpty()`、`complement()`、`v.* = .{...}` 这类可能先在栈上造一个临时值的写法。

## 检查（`check`）

走一遍当前的树，检查：每个节点的校验和、块号、事务号（不大于当前事务）、层数；键在节点里严格递增，并且都在父节点给的 `[下界, 上界)` 里（跳过 `ptrs[0].key`）；所有叶子在同一层；叶子的数据正好从块末尾往前挨着放、不和条目重叠；同一个块不被引用两次；当前的树不用 `pending` 里的块；`used` 正好等于树的块 + 超级块 + `pending`，`free_count` 和它一致。挂载时走的是同一个 `walk`（不数条目），所以坏块、写丢了在挂载时就能发现。

## 单元测试

都在主机上运行，用一块内存当磁盘（`bio` 的 `Device`）：

- `btree.zig`：键的顺序和 `successor`；叶子的插入、删除和数据的挪动；叶子分裂后两边都空出至少四分之一；`childFor` 把 `ptrs[0].key` 当负无穷；内部节点的插入、删除、分裂；校验和。
- `ctree.zig`：
  - 打乱顺序插入 400 个大小不一的条目，树长到至少 4 层；查找、遍历、`Exists`、`TooBig`、`NotFound`；随机改 300 次，提交，“重启”（清空缓存）之后内容不变；全部删掉，树缩回一个空叶子，除了超级块和它所有的块都空出来。
  - 没提交的改动重新挂载后没了；改了很多东西之后 `pending` 不空，`check` 一直确认当前的树没用到它们；没改东西的提交不写盘。
  - 磁盘满：放不下时 `NoSpace`、内容不变；删掉一些、提交之后又能放。
  - 坏块：根节点翻一位，挂载报 `Corrupt`；写丢了（新的根块换回旧内容），挂载报 `Corrupt`；最新的超级块坏了，挂载退回上一个事务，内容是那时的；两个都坏了是 `NotFormatted`。
  - 随机插入、更新、删除 1500 次，每一次之后都 `check`。
  - **掉电**：在一块 64 块的内存磁盘上做 20 个事务，每个 6 个随机操作（磁盘会满，满了的操作跳过），完整跑一遍共写 226 次盘。然后对每一个 N（0 到 226），从头再跑一遍，在第 N 次写之后掉电，那一次写分别是：完全没写进去、只写进前 16 字节（超级块的字段写了一半）、只写进前 2048 字节（节点写了一半）。之后清空缓存、重新挂载，要求：挂载成功；`check` 通过；内容正好是某一次提交之后的样子（每次提交前记下参照模型）；不早于最后一次 `commit` 返回了的事务（提交了就不会丢）；挂载之后还能接着改、提交。共 681 次掉电，整个单元测试约 1 秒。

  这个测试确实能抓住错误，验证过两种故意改坏的写法：释放已提交的树的块时不进 `pending`、马上空出来：成功写 9 次、第 10 次只写进前 16 字节时掉电，挂载失败（`Corrupt`）；超级块总写在第 0 块：成功写 6 次、第 7 次（超级块）只写进前 16 字节时掉电，挂载失败（`NotFormatted`）。最初分配用的是 next fit，第一种改坏的写法掉电测试没有发现（释放的块要绕一圈才会被重用），所以改成了 first fit。

## 限制和以后可以做的

- 还没有接进内核：文件系统（inode、目录、文件数据、`mkfs`、系统调用）是下一步。
- QEMU 上写盘是同步的（`bio.write` 等设备做完），但驱动没有协商、也没发 `VIRTIO_BLK_T_FLUSH`：数据交给了 QEMU，QEMU 自己（宿主机）掉电的话，超级块可能比前面的节点先落到宿主机的磁盘上。真机上要在写超级块之前发一次 flush。
- 不合并半空的节点；没有快照。
- 每个修改都复制整条路径，写放大比日志式文件系统大；一个事务里反复改同一批节点就不再复制。
- 挂载要读整棵树。
